## 案例 1｜AI 办公四工具：单任务 · 单交付物 · 一条最小工作流

**来源**：`微型PBL/AI办公/AI办公四工具微PBL选题.md`

### 结构

四道任务，每道用一个工具解决一类办公工序：

| 任务 | 角色/场景 | 输入 → 输出 | 主交付物 |
|---|---|---|---|
| 飞书 CLI | 财务/个人 | 5 条一句话消费 → 批量落库 → 统计 → 月报 | 记账多维表 + 月度财报文档 |
| WorkBuddy | 项目助理 | 4–6 份散材料 → 提炼 → 成稿 | 结构化周报 + 任务表 |
| OpenClaw | 市场/运营 | 行业信息源 → 每日提炼 → 推送 | 跑起来的早报管家 + 运行日志 |
| Claude Code | 数据分析/运营 | 脏 CSV → 清洗/透视 → 图表洞察 | 带图表的数据周报 |

### 可复用的设计动作

1. **一题只做一道工序**：不把「记账 + 财报 + 发群」拆成三个任务，而是合成一条最小闭环。
2. **标题带量化钩子**：明确写出「从 X 小时/手工，到 Y 分钟/自动」。
3. **交付物是工作资产**：不是一次性答案，而是下次还能复用的表、模板、命令、工作流。
4. **评分盯证据**：记录可抽查、数字可复算、命令可解释、凭证未公开。
5. **脚手架预置环境**：账号、授权、表结构、模拟数据都提前备好，课堂不把时间耗在安装上。
6. **正反例 + 常见错误**：每个任务都写「错误动作 → 正确做法」，并给 2–3 个换场景的变体。

### 不要照搬的地方

- 工具名和界面会过时；学的是「单任务 · 单交付物 · 最小工作流」的结构。
- 不是所有课都要做成 20–30 分钟；复杂系统可以扩成工作坊或项目任务。

## 案例 2｜企业级智能体工作坊：搭 + 测，交付「能干活且能干对」的系统

**来源**：`微型PBL/企业级智能体/企业级智能体工作坊微PBL选题.md`

### 结构

一个 2 小时工作坊，用「大脑 + 记忆 + 手脚 + 边界」四件套搭企业智能体：

```text
定题 → 搭骨架（System Prompt）→ 接知识（RAG）→ 加手脚（工具/工作流）→ 试与磨（测试/边界）
```

交付物三件：

1. 一个跑通的智能体（链接）。
2. 一张智能体设计卡（场景/用户/输入/输出/能力/知识源/工具/边界/验收）。
3. 一份测试与打磨记录（5 条问答，含 2 条陷阱题 + 修改痕迹 + 边界话术）。

### 可复用的设计动作

1. **用「部件」组织知识**：不是按平台菜单讲，而是按「一个能上岗的系统缺什么」组织。
2. **搭和测分开**：先让学员搭出来，再用陷阱题打它，最后加边界；避免「Demo 能跑 = 任务完成」。
3. **设计卡是思考支架**：逼学员在动手前说清用户、输入、输出、边界、验收。
4. **安全是评分维度**：内部资料、凭证、越权动作都写进验收，不是附录。
5. **时间紧时有保底链路**：保留「能基于资料准确回答」的核心，把重工具降为演示/加练。

### 不要照搬的地方

- 不是每个任务都要交付「设计卡 + 测试记录」；单点工具任务可能只需要一个文件和一份操作记录。
- 2 小时工作坊的粒度大于微任务，别把 20 分钟课硬塞成 5 个环节。

## 案例 3｜AI 私教三课：拆解 → 复刻 → 打磨

**来源**：`微型PBL/AI家教/AI私教三课微PBL选题.md`

### 结构

```text
① 解剖开源 Skill → 一份结构报告
        ↓ 结构理解
② 从零复刻最小私教 v1 → 能开课的 SKILL.md + 试跑记录
        ↓ 可运行的 v1
③ 加自适应分支 + 测试迭代 → v2 + 测试记录
```

### 可复用的设计动作

1. **每课一个独立成果**：报告、v1、v2 都能单独成立，同时又是下一课的输入。
2. **难度递进有认知依据**：先「看懂」（只读）→ 再「造出」（写）→ 再「改好」（测试迭代）。
3. **把「会用」升级成「会造」**：不是看教程，而是交付一个自己的工具。
4. **测试是交付的一部分**：v2 必须带「试→错→改→再试」的记录，不接受「写完就算」。
5. **同一骨架可换主题**：把「开课」换成「拆论文/备一节课」，任务结构仍然成立。

### 不要照搬的地方

- 拆解型任务需要一份高质量的「教材」；没有好样板时，改成诊断型或工具型。
- 复刻任务要写清「复刻 ≠ 抄袭」，必须用自己的话重述并标注出处。

## 案例 4｜第 1 章递进任务链：前序产出 = 后序输入

**来源**：`NexAI能力体系/第1章_实战任务提交方案.md`

### 结构

一章 4 个小节，每节 1 个任务，最终拼成一个智能客服 Prompt 原型系统：

```text
实战① Hello LLM（API 调用）
  → hello_llm.py
实战② 封装 LLMClient（Vibe Coding）
  → llm_client.py
实战③ 智能客服 Prompt + JSON Schema
  → prompt_template.md + schema.json
实战④ 整合对话系统 + 记忆 + 迭代
  → smart_cs.py + memory.py + iteration_log.md + 截图
```

### 可复用的设计动作

1. **从终点倒推**：先定「最终交付智能客服原型」，再倒推需要哪些中间件。
2. **证据链**：每个产出都是下一任务的输入，缺一个就拼不起来。
3. **任务卡字段固定**：任务名称、知识点、目标、内容、提交形式、实操耗时、脚手架、常见错误、连接下节。
4. **最后一题才整合**：前面不要求完整系统，只要求可复用的部件。
5. **提交包目录化**：明确文件结构，降低学员「交什么」的焦虑。
6. **评分分「达标/优秀」**：不只判对错，还看迭代质量、代码质量、证据完整度。

### 不要照搬的地方

- 不是每章都需要 4 个任务；3–6 个是常见范围，超过 6 个要合并。
- 代码任务的评分标准不能直接套到内容/分析任务；按成果类型换维度。

## 横向规律

从四个案例里反复出现的，不是某个工具，而是下面 8 条：

| 规律 | 具体表现 |
|---|---|
| **单任务单交付物** | 一个任务只解决一件事；主交付物 1 个，证据件最多 2–3 个 |
| **真实输入** | 给数据包、文档、坏样例、需求 brief，不从空白开始 |
| **真实对象** | 交付给客户/运营/项目组/评审，不写成「交给老师」 |
| **最小闭环** | 一条可跑通的工作流，而不是知识点的拼盘 |
| **量化钩子** | 说清「原来多久/多痛 → 现在多久/多好」 |
| **证据可查** | 日志、截图、测试记录、前后对照、来源链接 |
| **脚手架留白** | 模板、示例、常见错误齐全，但不给可直接交的答案 |
| **安全边界** | 能干活，更要能干对；真实操作要确认，数据要脱敏 |

### 任务设计时最值得抄的 3 个句式

1. **任务标题**：`<角色>用<工具/方法>把「<旧状态>」变成「<新状态>」，交付<成果>`
2. **任务要求**：`给定<输入>，完成<动作>，产出<交付物>，并用<证据>证明<验收点>`
3. **教师备注**：`本任务只教<刚好够用的知识>；不教<超纲内容>；卡点用<脚手架>兜住`
